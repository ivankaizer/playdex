# Performance requirements

The launcher must feel instant with a controller in hand. These budgets are requirements, not goals: a feature that breaks one is not done.

Measure on the target hardware class (a handheld such as the ROG Ally / Legion Go in Windows Full Screen Experience, and a desktop PC on a TV), on a release build.

## Budgets

| Metric | Budget | How it is measured |
|---|---|---|
| Input → visible focus change | ≤ 1 frame (16.7 ms at 60 Hz, 8.3 ms at 120 Hz) | Timestamp the input event in the host, then the next `requestAnimationFrame` after the focus class changes |
| Frame time while navigating and scrolling | p99 ≤ frame interval, 0 long tasks > 50 ms | Performance HUD (frame-time graph) and Chrome trace in WebView2 |
| Library size without degradation | 5,000 games, same budgets as 50 | Seeded library in the perf harness |
| Return to home after a game exits | ≤ 150 ms to an interactive home screen | The process stays resident; only window activation is measured |
| Cold start to interactive home | ≤ 500 ms with the host, ≤ 1.2 s including WebView2 creation | Process start → first interactive frame, logged by the host |
| Cover visible after its tile scrolls into view | ≤ 50 ms from the local thumbnail cache | Image `decode()` resolution time |
| Game exit detected | ≤ 250 ms | Process/job exit event → session end recorded |
| Host memory (resident, idle) | ≤ 80 MB host + ≤ 250 MB WebView2 | Task Manager private working set |
| CPU while idle on home or while a game runs | ~0% (no polling loops, no running animations) | ETW / Task Manager |

## Rules that keep the budgets

### Input
- Read the controller in the host on a dedicated thread (XInput, including the Guide button and rumble), and push events to the UI. The browser Gamepad API is a fallback only.
- The input thread must not allocate per event. Use the `SustainedLowLatency` GC mode.
- Held-direction repeat: 400 ms initial delay, then accelerate (from about 120 ms down to 60 ms). Filter duplicate events from virtual pads (Steam Input).
- Never turn controller input into synthetic keystrokes (Playnite does, and it queues input behind UI work).

### Rendering
- Moving focus must not re-render lists. Focus state lives in a store; only the item losing focus and the item gaining it update.
- Virtualize every grid and shelf; at most about 60 tiles are mounted at a time.
- Animate only `transform` and `opacity`. No animated `filter`, `box-shadow`, `backdrop-filter` or layout properties.
- No per-frame JS animations; use CSS transitions or WAAPI on the compositor.
- Background blur is pre-rendered into an image, never applied live over moving content.
- No idle animations on the home screen (the live-session pulse is the only exception and must stop when a game is in the foreground).

### Images
- Thumbnails are pre-generated by the host at exact tile sizes (1x and 2x) as WebP/AVIF, and served from disk.
- Load order: visible tiles first, then the next row; cancel loads for tiles that scroll away.
- Never download or decode full-size art on the UI path.

### Data
- The library is held in memory with precomputed sort keys. Filtering and sorting take < 2 ms for 5,000 games and run outside React render.
- The first screen renders from a cached snapshot passed in with the page. No network request blocks first paint.
- Library and Playdex sync run in the background and patch the snapshot.

### Startup
- Create the WebView2 environment in parallel with host initialization. Show a native splash if WebView2 is not ready.
- Code-split every non-home route. The home bundle stays under 150 kB gzipped JS.
- No plugin or integration work before first paint.

### Game tracking
- Event-driven, no polling loops: Windows Job Objects for games the launcher starts (they also catch child processes), and the Steam `HKCU\Software\Valve\Steam\Apps\<appid>\Running` value via `RegNotifyChangeKeyValue` for Steam games.

## Verification
- A perf harness (seeded 5,000-game library and a scripted controller replay) runs in CI and fails the build when a budget regresses.
- The in-app performance HUD (toggle with a controller chord) shows frame times, input latency and mounted-tile count.
